## Context

`README.md` presents face-recognition attendance as ShikshaSathi's headline feature. The legacy backend declares `opencv-python` and `mtcnn` as dependencies and has a scaffolded module shape (`app/ml/detector.py` → `embedder.py` → `matcher.py`) implying a detect-then-embed-then-match pipeline — but **all three files are empty**, never imported anywhere, and there is no working face-recognition code in the repository at all (`docs/AUDIT.md` §2.13, High finding H3, confirmed by a full-repo grep for `cv2`/`mtcnn`/`face_recognition` usage). `README.md` additionally describes two different, mutually-inconsistent plans for this feature at different points ("Demo data + basic structure" for an initial phase, "face-api.js / TensorFlow.js in browser" for a later optional phase) neither of which matches the OpenCV/MTCNN dependencies actually declared.

This means the choice of provider/approach was fully open when this ADR was first written — there was no existing implementation constraining it. That remains true at the point of decision: Phase 1–4 built no face-recognition code (`docs/LEGACY_MIGRATION_MAP.md`: both Face detection and Face embedding/matching are scoped as "Rewrite", i.e. greenfield), so this decision is made against a clean slate, not retrofitted onto anything.

## Evaluation criteria for the decision (applied below)

These are the criteria this ADR was written against when still "Pending"; they are preserved here unchanged and are the same criteria the comparison in "Decision" below actually applies, item by item.

- **Accuracy under real classroom conditions** — group photos, varied lighting, partial occlusion (masks, angle), which is the actual attendance-capture scenario, not single well-lit headshots.
- **Where inference runs** — server-side (Python, e.g. an OpenCV/MTCNN/FaceNet-style pipeline, or a hosted API) vs. in-browser (e.g. face-api.js/TensorFlow.js, as one of README's two stated-but-unbuilt plans suggested). This materially affects the architecture boundary in `docs/ARCHITECTURE.md` §9 (whether raw images ever need to leave the client) and privacy posture for biometric data.
- **Licensing and cost** at the free/low-tier hosting level this project targets (`README.md` explicitly frames the project as "Free-Tier Ready").
- **Data protection implications** — face embeddings are sensitive biometric data; some jurisdictions regulate this specifically. Storage/retention/consent handling needs to be designed alongside the provider choice, not bolted on after (see `docs/BIOMETRIC_DATA_POLICY.md`, added alongside this ADR's acceptance).
- **Maintenance burden** — MTCNN (declared but unused in the legacy app) is a reasonable, well-known face-detector choice, but the broader Python face-recognition ecosystem has actively-maintained and less-maintained options; pin to something with an active maintenance story.
- **Integration fit** with the module boundary already proposed in `docs/ARCHITECTURE.md` §9 (`detect` / `embed` / `match` as three swappable stages) so the provider can change later without a full rewrite.

## Alternatives compared

The three alternatives originally listed as "to evaluate at decision time" are the three actually compared below, unchanged in identity:

1. Server-side Python pipeline continuing the legacy dependency direction (OpenCV + an embedding model), running inside `backend_v2`.
2. In-browser inference (face-api.js / TensorFlow.js) — README's other stated-but-unbuilt option.
3. A hosted third-party face-recognition API.

### Comparison matrix

| Criterion | 1. Server-side local (chosen) | 2. Browser-side inference | 3. Hosted third-party API |
|---|---|---|---|
| Classroom/group-image suitability | The specific detector this ADR names (YuNet) is trained and benchmarked on WIDER Face, a multi-face, varied-scene dataset, with published "easy/medium/hard" accuracy tiers — a reasonable *structural* fit for group photos. Actual accuracy on this project's real classrooms is **unmeasured** and must be verified in Stage 3, not assumed here. | `face-api.js`'s SSD-MobileNetV1 detector can find multiple faces per frame, but its reference demos and documentation center on single/few-face webcam use, not dense classroom photos; fit is less clearly established than option 1. | Major hosted vendors generally support multi-face detection on large, varied training sets, and are plausibly strong here — but exact behavior is the vendor's own roadmap, not something this ADR can pin down or verify. |
| Privacy / raw-image movement | Raw images and any intermediate crop/embedding stay inside infrastructure the school already controls; no image or embedding needs to cross the network to a third party for a recognition attempt. | Pixels never *have* to leave the capturing device to reach a backend — but the actual attendance flow here is a teacher/admin-operated device capturing a whole classroom, not each student's own device, so the usual "client-side privacy" argument for this pattern is weaker than it looks; an uncontrolled browser/OS on that device is also a less auditable trust boundary than a server this project runs. | Weakest on this dimension by construction: a raw image or face crop must leave the school's infrastructure and cross the network to a third party for every recognition call. This is exactly the kind of movement of children's biometric data `docs/BIOMETRIC_DATA_POLICY.md` is written to avoid by default. |
| Free/low-cost hosting viability | No per-call vendor billing; cost is CPU time on infrastructure already provisioned for `backend_v2`. Best fit for `README.md`'s own "Free-Tier Ready" framing. | No server inference cost, but adds real (if different) cost: megabytes of model weights downloaded per browser session unless self-hosted and cached, plus a materially larger frontend engineering surface. | Weakest fit for "Free-Tier Ready": hosted face APIs are typically metered per image/call, so cost scales directly with attendance volume rather than being a fixed infrastructure cost; any free tier is usually time-boxed or capped in ways a growing deployment will eventually exceed. Exact current pricing/limits are the vendor's to change and are **not asserted here** as a specific number. |
| CPU-only runtime viability | **Confirmed, not assumed:** the OpenCV Zoo's own published benchmark table reports YuNet inference times on an Intel CPU, a Raspberry Pi CPU, and even a 1 GHz RISC-V SoC with no GPU — CPU-only is an explicitly supported, benchmarked configuration, not a hopeful extrapolation. | Works on CPU via TensorFlow.js's CPU/WASM backends, but noticeably slower without the WebGL backend, and performance varies by whatever device happens to be running the browser — a variable this project's own architecture has no control over. | Not this project's concern — inference runs on the vendor's infrastructure. A plus for this project's own compute budget, at the cost of the privacy/cost rows above. |
| Optional GPU support | For the YuNet detector itself, OpenCV's own DNN backend/target selection (`cv2.dnn`'s backend/target enums) exposes a GPU path — but the standard pip `opencv-python-headless` wheel is CPU-only; a CUDA-accelerated `cv2.dnn` backend requires a custom OpenCV build from source, not asserted as available out of the box here. Device selection is still a configuration value (`Settings.FACE_INFERENCE_DEVICE = "cuda"`), not a code fork, whichever way it is ultimately satisfied. If a Stage 3 embedding-model adapter separately uses `onnxruntime`, `onnxruntime-gpu` would be *that* adapter's own optional GPU path — not something the detector needs. | Depends on the browser's WebGL backend, itself dependent on the end user's device/driver/browser combination — not a setting this project controls the way a server's device flag is. | Entirely the vendor's concern; not a knob this project exposes either way. |
| Dependency and model size | The detector needs only `opencv-python-headless` (tens of MB, deferred to Stage 3 — **not added in Stage 1**), since OpenCV's DNN module parses and runs the YuNet `.onnx` file itself via its own built-in ONNX importer — the separate `onnxruntime` package is not required for the detector at all. YuNet's own model file is small (sub-megabyte, per the OpenCV Zoo repository). The paired embedding model's size (and whether its adapter needs `onnxruntime`) depends on which model Stage 2/3 selects (see "Deferred" below). | The original `face-api.js` bundles multiple TensorFlow.js models (detector + landmarks + recognition + expression), several MB each; a real integration also pulls in `tfjs-core` itself. | Smallest local footprint of the three — typically a thin HTTP client SDK, no model weights to vendor at all. |
| Licensing considerations | **Mixed — see "Licensing: what is actually confirmed" below.** The OpenCV Zoo repository itself is Apache-2.0, and the specific detector this ADR names (YuNet) is explicitly published as MIT-licensed. The embedding-model half of the pipeline is **not** locked in this ADR because of an unresolved upstream licensing question — treated here as an explicit blocker for that one component, not glossed over. | `face-api.js` and its actively-referenced fork are both MIT-licensed — no licensing blocker on this axis. | Not an open-source license question at all, but a commercial Terms of Service / data-processing agreement — a different review track (procurement/legal) than either other option, and one this rebuild's own instructions have repeatedly said not to resolve without jurisdiction-specific review. |
| Offline operation | Once model files are vendored locally (a one-time, build/setup-time step — not resolved in this ADR), inference requires no network call at request time. | Once weights are cached client-side, similarly offline at request time — but weights must still be fetched to every new device/browser profile the first time, over the open web unless self-hosted. | **None.** Every recognition attempt requires network reachability to the vendor; a connectivity loss on either side blocks recognition entirely — a poor fit for a school that may have unreliable connectivity. |
| Maintenance burden | OpenCV is a large, actively-maintained upstream project with frequent releases; the OpenCV Zoo companion repository supplying the YuNet model is itself actively maintained. Mostly "bump versions periodically." (If a Stage 3 embedding-model adapter separately adds `onnxruntime`, that is a Microsoft-maintained cross-platform project — a reasonable maintenance profile too, but not asserted as already in place in Stage 1.) | **Confirmed unmaintained lineage:** the original `justadudewhohacks/face-api.js` package's own npm registry page shows its latest version (`0.22.2`) was last published in March 2020 — no release since. Separately, the actively-referenced community fork, `@vladmandic/face-api`, states in its *own* README that it is "completely superseded by" the maintainer's newer library, Human — that statement is the fork's, about itself, not a claim about the original `face-api.js` package's own README. Either way, this is real, sourced churn in a small ecosystem, not incidental trivia. | Low local code-maintenance burden (no model files, no inference code to keep working) — but trades that for vendor lock-in, API/response-shape changes outside this project's control, and a recurring procurement/compliance review the other two options don't require. |
| Testability | Fully local, deterministic, no network/vendor account required — fits this project's existing pytest/httpx testing convention directly (see `app/tests/test_face_recognition_contracts.py`, added in this checkpoint, which already tests the contracts this way with zero model dependency). | Hard to exercise in this backend's existing pytest/CI setup at all — would need a headless browser or a Node.js/TensorFlow.js polyfill layer (per `face-api.js`'s own documented `node-canvas` workaround), a different testing stack than this project uses anywhere else. | Testable via the vendor's SDK, but a real integration test needs either live vendor credentials (unavailable and undesirable in CI) or a mocked HTTP layer — less deterministic than a fully local pipeline either way. |
| Provider swapability | The `detect`/`embed`/`match` `Protocol` boundary (`app/modules/face_recognition/protocols.py`, this checkpoint) means OpenCV (and whatever runtime a Stage 3 embedding-model adapter chooses) is an implementation detail behind an interface; a different local library, or even a hosted API, could later implement the same Protocols without changing any calling code. | Tightly coupled to whichever JS/TensorFlow.js library is chosen; swapping later is realistically a frontend rewrite of the recognition path, not a backend interface swap. | In principle fine behind the same Protocol boundary (a hosted-API adapter is just another `FaceMatcher`/`FaceDetector` implementation) — but every vendor's response shape and error semantics differ, so swapping vendors later is a non-trivial adapter rewrite in practice, not a config flag. |
| Failure behavior | Fails within the same process/request — no separate network dependency to time out or degrade independently; a missing/corrupt model file is a fail-fast condition Stage 3 can check at startup, not a silent per-request failure. | Fails silently/differently across a fleet of uncontrolled student/teacher devices and browser versions — much harder to reason about centrally than a single controlled server process. | A vendor outage or network partition becomes an attendance-marking outage. Phase 4's attendance core has no dependency on third-party uptime today (`docs/HANDOVER_PHASE_4.md`); Phase 5 should not introduce one by default. |
| Data-retention implications | Retention of any intermediate biometric artifact (aligned crop, embedding) is governed entirely by this project's own `docs/BIOMETRIC_DATA_POLICY.md` — one policy, one storage boundary. | If matching happens entirely client-side, there may be no server-side record of what was compared against what at all — a poor fit for this project's own audit-trail requirement (every attendance-relevant decision must be centrally auditable, `docs/adr/0010`). | Retention is governed partly by the vendor's own data-processing terms *in addition to* this project's policy — a second retention regime to track and reconcile, which the biometric data policy explicitly wants to avoid. |

### Licensing: what is actually confirmed, and what is an open blocker

This ADR treats licensing as a hard gate, not a detail to note and move past:

- **Confirmed permissive:** the OpenCV Zoo repository (`opencv/opencv_zoo`) is published under the Apache-2.0 license, and the `face_detection_yunet` model directory specifically states "All files in this directory are licensed under MIT License." Both are compatible with this backend's own `Proprietary` license declaration (`backend_v2/pyproject.toml`).
- **Not confirmed — treated as a blocker, not assumed permissive:** the paired embedding model most commonly demonstrated alongside YuNet in OpenCV's own tutorials (`face_recognition_sface`, "SFace") has an unresolved upstream question about its own license. A GitHub issue on the `opencv/opencv` repository (issue #21192, "What is the license for SFace model?") states the model's license "is not explicitly indicated." **That issue is marked `Closed`** — it is not, as an earlier draft of this ADR incorrectly stated, still open — but closing an issue is not the same as an explicit licensing answer, and no comment resolving the question is visible in the issue itself. Separately, the `opencv/opencv_zoo` repository's `models/face_recognition_sface/` directory does contain a `LICENSE` file (Apache-2.0 text) as of this ADR's research. This ADR does **not** treat that file alone as a confirmed, independently-verified grant for the model weight specifically: it may simply mirror the repository's own top-level license rather than being a dedicated statement of redistribution rights for a weight file whose training/provenance traces to a separate upstream research project (`zhongyy/SFace`, referenced directly in issue #21192). In short: **the cited issue and directory-level documentation do not, on their own, amount to a confirmed explicit SFace model license.** SFace remains unselected until model provenance and redistribution rights are independently verified — not inferred from a directory-level license file alone. Stage 2/3 must do one of the following before vendoring any embedding-model weight file:
  1. Independently verify provenance and redistribution rights for the specific weight file (e.g. tracing it to the upstream `zhongyy/SFace` project's own license terms, or obtaining an explicit maintainer statement that the `opencv_zoo` directory `LICENSE` file is intended to cover the model weight itself, not just the repository's surrounding code), or
  2. Select a differently, unambiguously licensed embedding model instead (e.g. an Apache/MIT/BSD-licensed alternative whose weight-level license is stated by its own authors, not inferred), documented as an addendum to this ADR when that choice is made.
- No model weight of any kind is downloaded, vendored, or committed in Stage 1 — this section is a documented decision constraint for Stage 2/3, not a completed procurement step.

### Accuracy: explicitly not claimed

No accuracy threshold, benchmark result, or "works well enough" claim is made anywhere in this ADR for this project's actual classroom conditions. The WIDER Face benchmark numbers cited above describe YuNet's published performance on a third-party academic dataset, not this project's students, cameras, or classrooms. Real accuracy against this project's own data can only be established once Stage 3 implements a real pipeline and Stage 5 runs actual verification — see `docs/IMPLEMENTATION_PLAN.md` Phase 5, Stage 5's acceptance criteria, which explicitly requires not silently claiming an untested threshold has been met.

## Decision

**Server-side local Python inference (alternative 1) is accepted as the MVP architecture**, implemented behind the provider-neutral `detect` / `embed` / `match` boundary already proposed in `docs/ARCHITECTURE.md` §9 and now given concrete typed contracts in `app/modules/face_recognition/domain.py` and `protocols.py` (this checkpoint).

This decision is made on the comparison above as a whole — no single row was decisive alone, but privacy/raw-image movement, offline operation, free-tier cost fit, testability, and this backend's own async-Python/pytest architecture point the same direction together, while option 3's per-call cost and required network dependency are a poor match for a project explicitly framed as "Free-Tier Ready," and option 2's unmaintained reference implementation and lack of a workable server-side test story are a poor match for how this backend is already tested.

### What is decided vs. deferred (do not conflate these)

**Decided by this ADR:**
- Inference runs server-side, inside `backend_v2`, as Python code — not in the browser, not via a hosted API.
- The runtime is CPU-first (`Settings.FACE_INFERENCE_DEVICE` defaults to `"cpu"`), with GPU (`"cuda"`) supported later as a configuration change, not an architecture change.
- The face **detector**: YuNet (MIT-licensed, confirmed above) will be loaded through OpenCV's DNN/`FaceDetectorYN` API using `opencv-python-headless`. The separate `onnxruntime` package is **not** required to run this detector — OpenCV's own DNN module parses and executes the YuNet `.onnx` file directly through its built-in ONNX importer. `onnxruntime` is deferred until (and only if) a selected embedding-model adapter genuinely needs it (see "Consequences" below).
- Every one of the three stages is accessed only through the `FaceDetector` / `FaceEmbedder` / `FaceMatcher` Protocols (`app/modules/face_recognition/protocols.py`) — no provider-specific type crosses that boundary.

**Explicitly deferred to Stage 2/3 (not decided here):**
- The specific face **embedding** model (blocked on the SFace licensing question above, or an alternative selection).
- Exact `FACE_MATCH_THRESHOLD` / `FACE_MATCH_AMBIGUOUS_MARGIN` calibration — Stage 1's config defaults (`0.90` / `0.05`) are conservative placeholders, not calibrated values (see `app/core/config.py`).
- Model file provenance, integrity verification (e.g. checksum pinning), and the exact vendoring/download mechanism.
- Any GPU rollout — CPU is the only runtime this ADR expects for the MVP.

## Consequences

- **Dependencies deliberately NOT added in Stage 1:** `opencv-python-headless` and its transitive `numpy` dependency are **not** present in `backend_v2/pyproject.toml` as of this checkpoint. Stage 1's contracts (`app/modules/face_recognition/domain.py`) deliberately store embeddings as a plain `tuple[float, ...]` and images as opaque `bytes` specifically so no such dependency is required yet, per the Stage 1 brief's instruction to add only dependencies Stage 1 itself imports. Stage 2/3 is expected to add `opencv-python-headless` (and accept `numpy` transitively) when real detector code is written — not before. **`onnxruntime` is a separate, further-deferred decision:** it is not needed to run the YuNet detector at all (OpenCV's own DNN module handles that internally), so it should be added only if and when a selected embedding-model adapter genuinely requires the standalone ONNX Runtime engine — not bundled in alongside `opencv-python-headless` by default.
- **Embedding model choice is a real, tracked open item**, not a silent gap — see "Licensing" above. Stage 2/3 must resolve it before any model weight is vendored.
- **Fallback/failure behavior for Stage 4** (not built yet, recorded here so it isn't invented ad hoc later): a provider failure (`FaceProviderUnavailableError`) or an `UNKNOWN`/`AMBIGUOUS` match result must never silently mark attendance. `docs/BIOMETRIC_DATA_POLICY.md` requires low-confidence/ambiguous results to require human confirmation, and any actual attendance write must go through the existing Phase 4 `AttendanceService`, never a direct write from the recognition path.
- Phase 5 Stage 2 (enrollment, secure photo ingestion) may now begin in a future session, since this ADR is no longer blocking it — but Stage 2 is explicitly **not** started in this checkpoint.
- Because Stage 1 implements no inference, accepting this ADR costs nothing in migration effort — there is no existing code this decision needs to be reconciled against (`docs/LEGACY_MIGRATION_MAP.md`: both Face detection and Face embedding/matching remain scoped as "Rewrite").
